# Sanic-Admin v0.2.1 Release Notes

> **Status: draft.** v0.2.1 is a maintenance release on top of [v0.2.0](v0.2.0-release-notes.md) — it carries no new features. This document records what changes relative to v0.2.0.
>
> The code-fix section is a placeholder until the implementation lands; the documentation corrections below are complete and verified.

---

## What this release is about

v0.2.0 established a working, installable, documented baseline (see the [v0.2.0 release notes](v0.2.0-release-notes.md)). v0.2.1 closes the items that v0.2.0 deliberately deferred to a later patch:

- the two defects in the system-settings interface that v0.2.0 recorded as *known limitations*;
- the documentation wording that still described the pre-release state after v0.2.0 had actually shipped.

Nothing else changes. The public API, the configuration contract and the deployment path are unchanged.

---

## Code fixes

### G1 — the system-settings resource (F7) and list pagination

Closes the two sub-items of [v0.2.0 known limitation #18](v0.2.0-release-notes.md), except the value-length cap, which is listed as a remaining limitation below.

| Defect | Before | After |
|---|---|---|
| `is_public` was coerced with `bool(...)` | `bool("false")` is `True`, so a client sending the string `"false"` silently **enabled** a public setting | parsed explicitly by `_parse_bool()`; a value that is neither a boolean nor a recognised string is rejected with a 400 `VALIDATION_ERROR` instead of being silently treated as `False` |
| `description` and `category` were not length-checked | a value longer than the model's column width was accepted and only failed (or was truncated) at the database | `description` ≤ 255 and `category` ≤ 50 are checked in `_validate_text_fields()`, which runs on every write path; over-length input is rejected with a 400 |
| a soft-deleted key could not be re-created | soft delete only sets `deleted = True` while `key` stays `unique=True`, so re-creating the key always failed with 409 | the soft-deleted row is **revived** (its `deleted` flag cleared and the new value written); a 409 is returned only when a **non-deleted** row with the same key already exists |

The same lane also makes the `settings` and `files` lists share one `parse_pagination` helper, so an
out-of-range `page` is clamped to `MAX_PAGE` and answered **200** instead of the 500 that an
unclamped offset produced.

### G2 — the AMIS static mount and the 405 `Allow` header

Two security-related fixes, plus the method-semantics cleanup that came with them.

| Defect | Before | After |
|---|---|---|
| the whole `amis/` directory was served statically | `server.js`, `package.json`, `nodemon.json` and `README.md` were reachable over HTTP (measured 200), leaking the dependency manifest and the development configuration | the application mounts only what the console needs at run time — the `pages/`, `sdk/`, `css/`, `js/`, `images/`, `fonts/` and `vendor/` sub-directories, plus `login.html` and `index.html` at the root. Anything outside that list has no route and answers **404** |
| a path containing a null byte raised an internal error | `GET /amis/%00` answered **500** — the static handler appended the raw path to a filesystem path and `posixpath` raised `ValueError: lstat: embedded null character in path` | the null byte is detected in `on_request` **after** unquoting (`request.path` is still percent-encoded, so the check has to run on the decoded value) and the request is answered **400** |
| 405 responses carried no `Allow` header | a method mismatch on a dynamic path could not tell the client which methods the resource supports | the 405 response now carries `Allow`, taken from the union of the methods of the **other** routes registered on the same path (the `*_method_not_allowed` fallback excluded). `OPTIONS` is left out, because the CORS preflight middleware answers it earlier with 204 |

The same commit also moves a number of routes onto the shared `register_view` helper so that a method mismatch answers **405** rather than the 404 that Sanic 23.6 produces when it swallows `NoMethod`: the four `settings` URIs and the six `upload` URIs.

### G3 — the AMIS console

| Defect | Before | After |
|---|---|---|
| `amis/login.html` ended with a duplicated, truncated HTML fragment | after a correct `</html>`, a stray `</title></head><body></body></html>` block was appended; browsers tolerated it, but the file was never valid | the fragment is removed; the document closes exactly once |
| the four list pages sent a stray query parameter | `requestAdaptor` returned `data: {}`; AMIS merges a `data` object into the query string, and an empty object is serialised with the array index `0` as the key, producing `...&0=%7B%7D` on every request — polluting access logs and handing the backend an unexpected parameter | `data: {}` removed from `account-list.json`, `role-list.json`, `log-list.json` and `setting-list.json`; pagination parameters continue to travel in the query string, whose handling is unchanged (`requestAdaptor`'s scope is `{api, context}`, and the existing `api.query` usage is unaffected) |

## Known limitations carried over from v0.2.0

Everything in the [v0.2.0 known-limitations list](v0.2.0-release-notes.md#known-limitations) still applies unless this document says otherwise. In particular:

- the single remaining Sanic 23.6 dependency advisory (`PYSEC-2026-4162`) is still deferred to the v0.3 Sanic 25 upgrade;
- `csrf_protect()` is implemented but not attached to any route, so there is still no CSRF protection in force;
- an unpaginated `page` parameter can still exceed the database's integer range and answer 500;
- the AMIS directory is still served verbatim, so its development files remain publicly reachable.

The `amis/login.html` trailing fragment listed in v0.2.0 is fixed by G3 above.

### New in v0.2.1 — the setting value still has no length cap, and the configured request-size limit does not work

Two related gaps remain, both deferred to v0.3:

- **The setting `value` has no length limit.** G1 added caps for `description` (255) and `category` (50), and the *type* of the value has always been validated against `value_type` — but the value itself is stored in a `TextField` and is accepted at any length.
- **The configured request-size limit is inert, and the real one is larger than the configuration claims.** `app/config.py` sets `MAX_CONTENT_LENGTH = 16 * 1024 * 1024` (16 MB), but Sanic 23.6 never reads that name — a recursive scan of the installed `sanic` package finds no reference to it. What Sanic actually uses is `REQUEST_MAX_SIZE`, whose default in `sanic/config.py` is **100 MB**; this project does not override it. For streamed requests Sanic sets `request.stream.request_max_size` to infinity (`sanic/app.py`). So the effective ceiling is 100 MB, or no ceiling at all for a streamed body — not the 16 MB the configuration advertises, and not "unbounded" either.

Together these mean a single setting value can be written at whatever size the client sends (up to that ceiling), and repeated writes can grow the database without a business-level bound. The fix belongs in v0.3: give `value` an explicit business limit enforced on every write path, and either make the request-size limit actually effective — by setting `REQUEST_MAX_SIZE` to the intended value — or remove the misleading `MAX_CONTENT_LENGTH` setting.

### New in v0.2.1 — the `Allow` header coverage is partial

v0.2.1 adds an `Allow` header to 405 responses, and it does so correctly for the routes that were
moved onto the shared `register_view` helper — the four `settings` URIs and the six `upload` URIs.
Measured on the release candidate: `DELETE /api/v1/settings` answers 405 with `Allow: GET, HEAD, POST`.

**`app/api/resources/log.py` was not moved onto that helper**, so a method mismatch on a `logs`
route still answers 405 **without** an `Allow` header (measured: `PUT /api/v1/logs` → 405, no `Allow`).
The routes in question are `GET /api/v1/logs`, `GET /api/v1/logs/<id>` and `GET /api/v1/logs/statistics`.
The scope of this release was the `settings` and `upload` routes, so this is a coverage gap rather
than a regression; wiring `log.py` in as well is left for v0.3.

## Upgrade notes

- No configuration change is required. Every variable that v0.2.0 introduced keeps its meaning.
- No data migration is expected from the changes described above.
- The v0.2.0 release notes and the public GitHub Release for v0.2.0 remain the reference for what v0.2.0 contained.
