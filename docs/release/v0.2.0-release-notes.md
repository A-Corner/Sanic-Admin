## What this release is about

v0.2.0 is the first version since 2023-09 that is meant to be **installable, runnable and usable**. It is a *re-baselining* release: the security baseline, the configuration contract, the entry point, the authentication layer and the packaging were rebuilt, and the documentation was rewritten to match the code instead of the other way around.

It is **not** a feature release: the management API, the admin console and the API documentation are closed out and working, but they are *restored*, not *extended*.

**Scope of this release.** v0.2.0 covers ten areas: **F1** authentication (register / login / logout, e-mail verification, an optional global second factor), **F2** RBAC (roles, permissions and per-role assignment), **F3** the management API (accounts, roles, profile, system settings, operation log, file upload, dashboard), **F4** API documentation (Swagger / ReDoc), **F5** the AMIS management console, **F6** a one-command run, **F7** an automated test suite and CI, **F8** the security baseline (no secrets in the tree, production fails closed, read-only SQL analysis, upload path hardening), **F9** documentation that matches the code, and **F10** the files that let AI agents take part in maintenance (`AGENTS.md`, issue and PR templates).

**Not in this release** (deferred to a later version): a Sanic / tortoise-orm major upgrade, per-account second-factor toggles, login rate limiting, a forced password change on first login, and the experimental Vue front end under `frontend/`.

## Known limitations

These are known and are stated here rather than discovered later.

### 1. One remaining Sanic 23.6 dependency advisory — deferred to v0.3

`pip-audit` on the installed dependency set reports **exactly one** known vulnerability:

```
Name    Version  ID               Fix Versions
sanic   23.6.0   PYSEC-2026-4162  24.12.1, 25.12.1
```

The fix requires a **major** Sanic upgrade (23.6 → 24.12/25.12), which is out of scope for v0.2.0. It is the **first item of the v0.3 upgrade plan**, together with the `tortoise-orm` 1.x migration.

### 2. The registration endpoint is vulnerable to account enumeration

`POST /auth/register` distinguishes identifiers that are already taken:

```
POST /auth/register  {"email": "<an existing address>", ...}
→ HTTP 400  {"error":"RESOURCE_ALREADY_EXISTS","message":"该邮箱已被注册","status":400}
```

The three variants are `该邮箱已被注册` / `该用户名已被注册` / `该手机号已被注册`, so an unauthenticated caller can probe for the existence of any of the three.

Note the contrast: **login does not enumerate** — it returns a uniform `用户名或密码错误` and deliberately spends equivalent time on the unknown-account and wrong-password paths. The registration path has no such protection.

Mitigation is planned for v0.3: return a uniform response for a taken identifier and send the "already registered" information out of band.

### 3. Per-account two-factor authentication is not implemented

Two-step verification exists and is exercised by `POST /auth/validate-2fa`, but it can only be switched **globally** — through the server-side `REQUIRE_TWO_FACTOR` setting. The decision is made by the server and any client-supplied parameter is ignored (`app/auth/routes.py:95`). There is **no per-account toggle**: an administrator cannot enable 2FA for one user and leave it off for another.

`REQUIRE_TWO_FACTOR` **is** wired into `app/config.py` on this release candidate — it is a boolean environment variable (`_bool_env()`, so `1`/`true`/`yes`/`on` enable it, `0`/`false`/`no`/`off`/empty disable it) read at `app/config.py:361` and consumed by `app/auth/routes.py:95`. It defaults to **off**, so two-step verification is disabled unless it is turned on explicitly.

What is missing is the *granularity*: there is a single global switch and no per-account setting. The account-switchable variant is explicitly deferred to v0.3.

It runs on every pull request against `master` and on every push to it.

### 5. The AMIS console is hosted by the backend, but its directory is served as-is

The console is mounted by the application under `/amis` (`app/static("/amis", …, index="login.html", name="amis")`), so it is entered at **`http://127.0.0.1:22222/amis/login.html`** — same-origin with the API, with the `HttpOnly` session cookie sent automatically and no CORS involved. The `amis/server.js` Node proxy remains only as an optional local preview aid.

Two consequences of hosting the directory directly are worth stating plainly:

- **Development files inside `amis/` are publicly reachable.** `amis/server.js`, `amis/package.json`, `amis/nodemon.json` and `amis/README.md` all return HTTP 200. None of them contains a secret, but the directory is served verbatim, so anything placed in it becomes public.
- **`/amis/%00` returns HTTP 500** instead of a 4xx.

Also note the trailing slash: `/amis/` shows the login page, while bare `/amis` returns 404 — Sanic's `DirectoryHandler` only performs the index lookup for paths ending in `/`.

### 6. The API documentation routes are mounted, but only when `ENABLE_API_DOCS` is on

`setup_docs()` is wired in `app/__init__.py` and is controlled by the `ENABLE_API_DOCS` setting, which defaults to **on in development** and **off in production**. In production the routes are therefore absent unless the variable is explicitly enabled — the same fail-closed posture the rest of the production configuration takes.

Note that `sanic-ext` also publishes an OpenAPI document of its own at `/docs/openapi.json`; it is a *different* generator from `app/docs/` and lists only the routes Sanic has actually registered. It answers **404 in development** (where `setup_docs()` takes over the `/docs` prefix) and 200 in production.

### 7. Test coverage is 50 % over `app/`

`pytest` reports **`95 passed`, 0 failed, 0 errors** (95 collected, ~54 s). The suite concentrates on the parts that carry the security and correctness weight — authentication, authorisation, account and role CRUD, upload path traversal, SQL read-only enforcement and the production fail-closed gates — but coverage over `app/` is only **50 %** (5535 statements, 2750 uncovered).

The thinnest areas are `app/web/routes.py` (0 %), the cache backends (`memory.py` 25 %, `redis.py` 21 %, `decorators.py` 27 %), `app/database/connection_pool.py` (20 %), `app/docs/decorators.py` (13 %) and `app/middleware/_headers.py` (11 %). Raising coverage is not a v0.2.0 gate, but it is the obvious next piece of work.

### 8. No published container image and no `pip` package

`Dockerfile`, `docker-compose.yml`, `.dockerignore` and `.env.example` are in the repository and the Docker path is exercised in CI (`.github/workflows/docker.yml`), but **no image has been pushed to a registry and no PyPI package exists**. The PyPI name `sanic-admin` is taken by an unrelated project, so publishing under it is not possible; a different name would have to be chosen first.

### 9. Some dynamic routes answer 404 instead of 405 for an unsupported method — deferred to v0.3

`app/api/resources/route_methods.py` exists precisely to make method mismatches answer **405** rather than 404: Sanic 23.6 swallows `NoMethod` inside `resolve()` and re-raises it as `NotFound`, so a dynamic path (`/api/v1/settings/key/<key>`) whose method is not registered reports "resource does not exist" instead of "method not allowed".

The helper is wired into some resources (`account.py`, `role.py`, `profile.py`) but **not** into others. `app/api/resources/setting.py` still registers with `v1_bp.add_route(...)`, so:

- `DELETE /api/v1/settings/key/<key>` → **HTTP 404** (should be 405).

The static routes (`/api/v1/settings`) already answer 405 correctly.

### 10. The 405 responses carry no `Allow` header — deferred to v0.3

The fallback handler in `app/api/resources/route_methods.py` returns a JSON body with status 405 but sets no `Allow` header, which RFC 9110 requires for a 405 response. Clients that rely on `Allow` to discover the supported methods of a resource will not find it.

### 11. The AMIS directory is served verbatim, so its development files are public — deferred to v0.3

Because the console is mounted as a static directory, `amis/server.js`, `amis/package.json`, `amis/nodemon.json` and `amis/README.md` are all reachable over HTTP with status 200. **None of them contains a secret**, but the directory is served as-is, so anything dropped into `amis/` becomes public. `GET /amis/%00` additionally returns **HTTP 500** instead of a 4xx.

### 12. Connection-pool semantics are only verified against SQLite — deferred to v0.3

The pool configuration and the health endpoint were exercised against SQLite only. MySQL and PostgreSQL were **not** run against a real server, and the multi-worker synchronisation race has not been reproduced or fixed.

### 13. Two production start-up gates beyond the secrets — deferred to v0.3

Independently of the two required secrets, a production instance has two further ways to refuse to start. Both fail closed, which is the right default but catches people out who set only the secrets.

- **Redis must be reachable.** `CACHE_TYPE` defaults to `redis` in production, and the Redis probe failing makes the application raise `ConfigError: production 环境 Redis 缓存不可用，拒绝降级启动` and exit with code 1 — even with both secrets present. Either provide a reachable Redis, or set `CACHE_TYPE=memory` deliberately (in-memory caching is per-process: it does not survive a restart and cannot be shared across workers).
- **`DATABASE_URL` must be set, and the default is MySQL.** Without it the application assembles a MySQL URL from `DB_HOST` / `DB_PORT` / `DB_USER` / `DB_PASSWORD` / `DB_NAME`. **`aiomysql` is not in `requirements.txt`**, so that path fails at import time with `ModuleNotFoundError: No module named 'aiomysql'` until a driver is installed by hand.

Both are verified by measurement; the README's *Deploying* section spells out a minimal production invocation that avoids them.

### 14. An unpaginated `page` parameter can exceed the database's integer range — deferred to v0.3

Resources that do not clamp the `page` parameter (the `settings` list, among them) accept any positive integer, and the value is used directly as an SQL offset. A `page` larger than the database's integer range — beyond 17 digits — makes the query fail with **HTTP 500**. A `page` within 14 digits works normally and returns 200.

Resources built on the shared `BaseResource` clamp `page_size` to `max_page_size` (`app/api/base.py:207`), but the `page` offset itself is not clamped anywhere.

This is registered as a follow-up and does not block the release; the exact behaviour is to be confirmed by the independent R1–R8 gate run.

### 15. CSRF protection is implemented but not enabled — deferred to v0.3

`csrf_protect()` (`app/middleware/security_middleware.py`) checks the `X-CSRF-Token` header against the `csrf_token` cookie for non-`GET` requests and answers 403 on a mismatch. **No route is decorated with it**, so there is currently no CSRF protection in force.

What stands in for it today: the session cookie is `HttpOnly` + `SameSite=Lax`, and the API carries credentials in the `Authorization` header rather than in a cookie. `SECURITY.md` records the same thing.

### 16. `amis/login.html` ends with a duplicated, truncated HTML fragment — deferred to v0.3

The file is 146 lines; line 137 is `</html>` and lines 140–147 repeat a stray `</title>`, `</head>`, `<body>`, `</body>`, `</html>` sequence, and the file has no trailing newline. Browsers tolerate it and the login page renders correctly, but the file is clearly assembled by concatenation and never validated. Left untouched in v0.2.0 because the baseline is frozen.

### 17. Legacy credentials in the repository history

The repository history contains a sample JWT private key, a default administrator password (`SAdmin@123`) and a SQLite database file. **All of these must be treated as compromised.** `SECURITY.md` states this and requires rotation. The current tree contains none of them — the old README references were removed in this release — but history rewriting was not performed for v0.2.0.

### 18. The system-settings value has no length limit, and a soft-deleted key cannot be recreated — deferred to v0.3

Two defects in the system-settings resource (`app/api/resources/setting.py`):

- **The stored value has no length limit.** The *type* of the value **is** validated — `validate_value_type()` (`app/api/resources/setting.py:111`) checks the value against the declared `value_type` (`string` / `int` / `float` / `bool` / `json`) and is called on every write path (`:217`, `:278`, `:336`, `:400`). What is missing is a **maximum length on the value itself**: the field is only checked with `Required()`, so a value of arbitrary size is accepted and stored.
- **A soft-deleted key cannot be recreated.** Soft delete sets `deleted = True` without removing the row (`app/models/base.py:68`), while `key` is `unique=True` (`app/models/system_setting.py:24`). The create path does not look for an existing soft-deleted row with the same key, so re-creating a deleted key hits the unique constraint and fails with **409** instead of restoring it.

Both are deferred to v0.3.

## Breaking changes and migration notes

| Change | Impact | Action required |
|---|---|---|
| The default administrator password `SAdmin@123` no longer exists | Anyone relying on the old default can no longer log in | Set `INITIAL_ADMIN_PASSWORD` before first start, or read the one-time password printed to stdout in development |
| All secrets now come from environment variables; the repository holds none | Deployments that relied on in-code defaults must be reconfigured | Provide `JWT_PRIVATE_KEY` and `INITIAL_ADMIN_PASSWORD` in the environment. In `production` a missing one **aborts startup** with exit code 1. `SECRET_KEY` and `PASSWORD_SALT` are accepted but currently unused — see the configuration reference |
| The entry point now reads host/port/workers from the environment | Inline `app.run(host=..., port=...)` overrides no longer apply | Set `HOST` / `PORT` instead of editing `main.py` |
| `SANIC_ENV` selects the configuration; `development` uses a local SQLite file and `testing` uses in-memory SQLite | Deployments that assumed MySQL by default will now get SQLite in development | Set `DATABASE_URL` explicitly for any non-SQLite deployment |
| `CACHE_TYPE` defaults to `redis` in production, and Redis failure is **fatal** there | A production deployment without a reachable Redis will not start | Provide a reachable Redis, or set `CACHE_TYPE=memory` deliberately |
| Session cookies are `Secure` in production | Plain-HTTP production deployments will lose the session cookie | Terminate TLS in front of the application, or run in a non-production environment |
| The `/v1` API blueprint, the admin console and the `/swagger` documentation routes are mounted now, but their paths differ from the 2023 API | A client written against the 2023 API will not find its endpoints | Use the generated OpenAPI document at `/swagger.json` as the source of truth for the current surface |
| The Docker quick start expects a `.env` file to exist before `docker compose up` | `docker compose up` fails immediately if `.env` is missing, instead of starting a container that crashes later | `cp .env.example .env` and replace every `change-me-*` placeholder first. The container runs with `SANIC_ENV=production`, so it refuses to start on a missing or placeholder secret |
| The Docker quick start publishes the application on host port **22230** (container port 22222) | Anything pointing at 22222 will not reach the container | Use `http://localhost:22230`. The pip path is unaffected and still listens on 22222 |
| Redis in the compose file is an **opt-in profile**, not a default service | `docker compose up` alone starts only the app; `CACHE_TYPE=redis` without Redis makes production refuse to start | `docker compose --profile redis up -d` when using the Redis backend |
| The legacy root-level modules (`auth.py`, `models.py`, `restful_api.py`, `configuration.py`, `utils.py`, `verification.py`, `exceptions.py`, `task.py`, `web.py`, `__init__.py`) and the `test/` directory were removed | Anything importing them breaks | Use the `app.*` packages instead |
| `requirements.txt` no longer pins the whole dependency tree | A rebuild may resolve newer minor versions than a previous build | Pin explicitly in your own deployment if you need reproducible builds |
| `frontend/` (Vue 3) is experimental and not maintained; AMIS is the front-end direction | Vue-specific work will not be merged | Target `amis/` |

---

## Upgrade path

1. Read [SECURITY.md](../../SECURITY.md) and rotate anything that was ever derived from the legacy defaults.
2. Provide the environment variables listed in [docs/configuration.md](../configuration.md).
3. `pip install -r requirements.txt`, then `python main.py`.
4. Confirm `GET /health` returns 200 and that the startup log contains **no** `[降级]` (degraded) lines.
5. Log in with the administrator account and confirm the session is issued.
