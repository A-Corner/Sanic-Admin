# Sanic-Admin v0.4.2 发布说明

**发布日期：2026-10-27。**

---

## 这一版做了什么

MCP 写入路径从「进程开关控制」升级为「账户权限控制」。

v0.4.0 引入写入工具时，唯一的门槛是启动参数 `--allow-write`——谁能拉起这个进程，
谁就能写提案分支。v0.4.2 把它接到项目已有的 RBAC 上：每次调用都要校验调用方是谁、
有没有 `spec:write` 权限，会话被吊销后下一次调用立即失效。

---

## Breaking change（行为变更，必须读）

### 只开 `--allow-write` 不再够用

| | v0.4.0 / v0.4.1 | v0.4.2 |
|---|---|---|
| 写入工具出现在 `tools/list` | 需 `--allow-write` | 需 `--allow-write`（不变） |
| 调用能否成功 | 能 | **还需** `SANIC_ADMIN_MCP_TOKEN` 且账户有 `spec:write` |
| 缺 token 时的表现 | — | 工具可见，调用报 `identity_not_configured` |

**影响谁**：任何在 v0.4.0/v0.4.1 上使用 `--allow-write` 的环境。升级后写入工具不会消失，
但调用会失败，直到配置好 token 与权限。这是**故意的 fail-closed**：宁可拒绝，
也不在身份不明的情况下继续写。

**代码依据**（`71a0394` 实测行号）：三个写入工具在入口处调用
`require_spec_write()`——`tools/mcp_server/write_tools.py:128`（propose）`:205`（list）
`:224`（discard），该调用位于一切副作用之前（不建 clone、不建分支）。未配置 token 时
抛 `identity_not_configured`（`tools/mcp_server/identity.py:62,101-129`）。

### 升级三步

```bash
# 1) 取一个会话 token（沿用现有登录流程，本版不新增长期 API token）
curl -s -X POST http://127.0.0.1:22222/auth/login \
     -H 'Content-Type: application/json' \
     -d '{"email":"<your-account>","password":"<your-password>"}' \
  | grep -i '^authorization'      # Bearer <JWT> —— 这个 JWT 就是 token

# 2) 用 token 启动 MCP（--allow-write 仍需保留）
SANIC_ADMIN_MCP_TOKEN='<JWT>' python -m tools.mcp_server --allow-write

# 3) 若使用非 admin 账户，先在角色管理里给该角色授予 spec:write
```

会话过期后重新执行第 1 步并重启 MCP 进程（本版无热重载，长期 API token 列为后续项）。

## 新增

### `GET /auth/whoami`（#27）

返回当前会话的 `account_id` 与合并后的权限表，供 MCP 侧判断 `spec:write`。

| 约束 | 行为 |
|---|---|
| 鉴权链 | 走与 HTTP API 相同的 `authenticate_request`，不另造一套 |
| 2FA 未完成 | **拒绝**（`requires_authentication` 默认 `require_second_factor=True`） |
| `must_change_password=True` | **拒绝**——本路径不在强制改密豁免白名单里（中间件 fail-closed），handler 内还有一次显式检查 |
| 返回内容 | 只有 `account_id` 与 `permissions`，不含邮箱、用户名 |
| 审计 | 每次调用写一条 `whoami`，含账户与结果 |

### `spec:write` 权限点（#27）

注册进 `ALL_PERMISSIONS`（`app/auth/permissions.py`）。`is_admin` 账户默认拥有；
普通角色在角色管理里显式授予。`spec` 同时被 `specgen` 列为**资源名保留字**——
否则业务规格生成同名权限点会覆盖它。

### MCP 写入工具的身份校验（#27）

`tools/mcp_server/identity.py`。要点：

- **token 来源**：环境变量 `SANIC_ADMIN_MCP_TOKEN`，用现有会话 JWT，不新增长期 API token。
- **回调目标**：默认只允许本机回环（`127.0.0.1` / `localhost` / `::1`，按完整 host 串精确匹配）；
  拒绝携带 userinfo / query / fragment 的 URL；非回环必须显式设
  `SANIC_ADMIN_MCP_ALLOW_REMOTE=1` **且** 强制 https。
- **传输**：超时 5 秒；**禁止跟随重定向**、**禁止走代理**（自建 opener）；失败不重试。
- **不打印**：token 不进日志、审计、错误消息；出口脱敏另有兜底。

#### 七种拒绝场景（全部 fail-closed，且零副作用）

| 场景 | 错误码 | 代码位置（`71a0394`） |
|---|---|---|
| 未配置 token | `identity_not_configured` | `identity.py:231`（`require_spec_write` 入口）/ `:101,107,114,124,129`（URL 校验分支） |
| token 无效 / 会话不存在 | `identity_invalid` | `identity.py:174`（401 分类）→ `:177` |
| 会话过期 / 被禁用 | `identity_invalid` | 同上（服务端 `Session.decode` 抛错后 whoami 返 401） |
| 2FA 未完成 | `identity_invalid` | 同上（`requires_authentication` 默认 `require_second_factor=True`） |
| 需要先改密 | `permission_denied` | `identity.py:179`（403 分类）→ `:182` |
| 没有 `spec:write` 权限 | `permission_denied` + 账户标识 | `identity.py:237`（集合判断） |
| whoami 服务不可达 / 超时 | `identity_unavailable` | `identity.py:186,200,203,205` |

「零副作用」的含义：**不建隔离 clone、不建提案分支**。校验在所有副作用之前执行
（`write_tools.py:128/205/224` 的 `require_spec_write()` 是第一行语句）。

#### 三条完整路径（代码依据、用户动作、错误码）

| 要素 | 内容 |
|---|---|
| **代码依据** | `write_tools.py:128,205,224` → `require_spec_write()`；实现于 `identity.py:219-240`；错误分类见上表 |
| **用户动作** | ① 登录取会话 JWT（`POST /auth/login` 的 `Authorization` 头，见下方「升级三步」）；② 启动 MCP 时**同时**给 `--allow-write` 与 `SANIC_ADMIN_MCP_TOKEN=<JWT>`；③ 非 admin 账户需在角色管理里给角色授予 `spec:write` |
| **配错会看到什么** | 缺 token → `identity_not_configured`（提示「需要配置 SANIC_ADMIN_MCP_TOKEN」）；token 失效 → `identity_invalid`（提示「token 无效、过期或 2FA 未完成」）；无权限 → `permission_denied`（提示含 `account_id` 与「没有 spec:write 权限」）；服务没起 → `identity_unavailable`（提示「服务不可达——按 fail-closed 拒绝」） |

### `discard_proposal` 的删除条件

`discard_proposal` **不是**只按 `proposal/` 前缀删除，而是三重条件同时成立
（`tools/mcp_server/git_isolation.py`）：

1. 分支名是 `proposal/` 前缀
2. 存在归属标记 `refs/specgen/proposals/<name>`（证明是本工具创建的）
3. 标记指向的 SHA 等于分支当前 SHA（证明分支未被改动）

删除使用原子的 `update-ref -d refs/heads/<branch> <expected>`——若分支在「比对 SHA」
与「实际删除」之间被改动，git 自身会拒绝（TOCTOU 窗口由原子性封住）。

只按前缀删是危险的：任何人手工建一个 `proposal/xxx` 都能被删掉，而删除不可逆。

> **勘误（2026-10-28）**：本版发布说明的「已知限制」表（`v0.4.2` tag 正文，2026-10-27
> 发布的那一份）把 `discard_proposal` 写成「只按 `proposal/` 前缀判定」。发布说明原文
> **低估了**实现：`tools/mcp_server/git_isolation.py:573-637`（`discard_proposal` 全函数）的实际条件是本节列出的
> 三重条件（前缀 + 归属标记存在 + 标记 SHA == 分支当前 SHA），且删除用带期望值的原子
> `update-ref -d <ref> <expected>`，TOCTOU 窗口由 git 自身封住。原文保留不改，
> 以本勘误为准。

## 新增（续）：生成资源 CRUD 审计日志（#35，B6 / SA-v042-AUDIT）

生成器现在为每个生成资源的写操作自动写审计日志——`POST` / `PUT` / `DELETE` 三处，
在业务写入**成功之后**记录。

| 记什么 | 不记什么 |
|---|---|
| actor（账户 id + 用户名快照）、resource、action、id、IP、User-Agent | **字段值一律不记** |
| 变更的**字段名列表**，如 `fields=status,priority` | 例如 `status='in_progress'` 里的 `in_progress` 不进日志 |

`detail` 的实际形态（发布前实测）：

```
CREATE detail = 'id=1 fields=customer_id,priority,status,title'
UPDATE detail = 'id=1 fields=status'
DELETE detail = 'id=1'
```

设计取舍：资源里可能有手机号、邮箱、金额，**值进日志等于绕过脱敏**——所以只记名。

查询：`operation_type` 存**资源名**（如 `ticket`），与认证审计的 `operation_type="auth"`
是两个命名空间，互不冲突。可用 `/api/v1/logs?operation_type=ticket` 精确过滤。

覆盖范围：软删（`soft_delete: true` 的资源）与硬删两条路径都写审计，已分别实测。

### 实现位置（按 `4cdc97f` 实测，已逐行验证）

| 实现 | 位置 | 该行原文 |
|---|---|---|
| `record_resource_event()` 定义 | `app/services/audit.py:113` | `async def record_resource_event(` |
| 动作白名单 `RESOURCE_ACTIONS` | `app/services/audit.py:110` | `RESOURCE_ACTIONS = frozenset({"create", "update", "delete"})` |
| `detail` 构造（只拼 id 与字段名） | `app/services/audit.py:144-148` | `parts = [f"id={object_id}"]` / `parts.append("fields=" + ",".join(...))` |
| 审计失败被吞（旁路） | `app/services/audit.py:162-169` | `except Exception:` → `logger.warning("写入资源审计日志失败（已忽略）…")` |
| 生成器接入 · create | `tools/specgen/render_py.py:303` | 在 `obj = await {cls}.create(**payload)` 之后 |

## 修复

### 「全权限角色」判定排除 `spec`（#27）

`app/api/resources/role.py` 判断一个角色是否「授予全部权限」时，比较集来自权限注册表。
新增 `spec` 权限点后，存量自建的全权限角色因为 permissions 里没有 `spec` 键，会被判成
**非**全权限，从而失去「受保护管理员」身份——非管理员账户就能凭 `account:update`
撤销它的 admin 角色或改邮箱。这与 v0.4.0 修过的生成资源问题是同一条路径，现在一并排除。

v0.4.1 的验证节写「发布树 `c08bd21`（本版 squash 提交）上的实测」，但 v0.4.1 的 tag

### 审计写入失败不阻断业务

- **审计写入失败不阻断业务，也不回滚已完成的写入。** 生成的资源在
  `POST`/`PUT`/`DELETE` 成功**之后**才写审计；若审计写入失败（日志表不可写、
  迁移未执行等），只记一条 warning，业务请求仍返回成功、数据已落库。
  这是有意的取舍——宁可少一条日志，也不让写请求因旁路失败而失败。
  **依赖审计日志做合规追溯的部署，需要监控 `app.services.audit` 的 warning**，
  否则会出现「数据变更了但查不到记录」的静默缺口。
