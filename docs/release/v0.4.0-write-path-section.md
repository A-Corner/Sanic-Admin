### MCP 写入路径（原型，默认关闭）

只读层负责「看和校验」，写入层负责「出提案」——但**不负责合并**。

```
propose_spec_change(resource, yaml_text, base_ref="master")
    → 隔离 clone 里写规格 → commit → fetch 回用户仓库的 proposal/<branch>
list_proposals()
    → 列出提案分支与 commit
discard_proposal(branch)
    → 删掉提案分支
```

**这三个工具默认不注册**，必须用 `--allow-write` 启动才出现在 `tools/list` 里。
理由：MCP 是 stdio 本地进程，没有账户体系；默认暴露写能力等于「谁能拉起进程谁就能写」。

### 「AI 不能 push 或合并」是机制保证，不是约定

四层，逐层收口：

| 层 | 做法 |
|---|---|
| **一、clone 里没有推送目标** | 不带 remote；另把 clone 的 `.git/config` 直接改成 `push.default=nothing`、`credential.helper` 置空——不给凭据可用 |
| **二、即使有人加了 remote，pre-push hook 也无条件拦截** | hook 里 `exit 1`；且 `core.hooksPath` 显式指向 clone 自己的 hooks，防止用户全局 `hooksPath` 让我们的 hook 失效 |
| **三、工具代码的 git 命令白名单** | 子命令级 + **参数级**——`clone --upload-pack=<cmd>` 这类「子命令合法但参数能执行任意程序」的写法被挡住 |
| **四、合并能力根本不存在** | **刻意不实现 `apply_proposal`**。把提案写回主工作区等于绕开「人来合并」；应用应由人执行 `git merge` / `git cherry-pick` |

另有两项隔离措施（不是独立层，而是贯穿各层的运行前提）：`GIT_CONFIG_GLOBAL=/dev/null`
与 `GIT_CONFIG_NOSYSTEM=1`，确保不读用户/系统的 git 配置。

### 原型的已知限制

| 限制 | 说明 |
|---|---|
| `discard_proposal` 只看 `proposal/` 前缀 | 不校验分支是否由本工具创建。前缀目前足够区分，但不够强 |
| 24h 残留清理是 TODO | 靠 `finally: shutil.rmtree()`；进程被 kill 时临时 clone 会残留。自动回收可能删掉人正在看的东西，故留到下一轮 |
| 仅本地 stdio，无账户级权限 | `--allow-write` 是**进程级**开关，不是账户级 RBAC |
| `describe_proposal` 未实现 | 查看单个提案的完整 diff 需人工 `git show` |
| 生成器与迁移未接线 | 最小原型只做「写规格 → 提交 → fetch」；生成与迁移走已有的 `preview_generate` 路径，接线留到下一轮 |
| 审计写 stderr，不写数据库 | MCP 侧不强制依赖运行中的服务；审计内容不含规格全文 |

完整设计与实现清单见 [docs/mcp-write-path.md](../mcp-write-path.md)。
