# Sanic-Admin v0.3.0 Release Notes

> **Status: released 2026-10-23.** v0.3.0 is the first feature release on top of the v0.2.x maintenance line. It moves the framework to the supported Sanic 25 line (removing the last dependency advisory), hardens the security surface (setting-value cap, a request-size limit that actually works, CSRF, login rate-limiting), deduplicates the AMIS routing, and grows the test suite to **320 cases** with app/ coverage at **68%**.

## What this release is about

v0.2.1 closed the defects that v0.2.0 had deferred and recorded the rest as known limitations. v0.3.0 works through that list:

- **P3 — Sanic 25.** `sanic 23.6.0 → 25.12.1`（sanic-routing / sanic-ext / sanic-testing 锁步升级）。这是消除最后一条依赖公告（`PYSEC-2026-4162`）的唯一路径，也让框架回到受支持线。
- **P1 — the setting value gets a real length cap, and the request-size limit becomes real.** Closes the value half of v0.2.0 limitation #18 and the inert-`MAX_CONTENT_LENGTH` limitation recorded in the v0.2.1 notes.
- **P2 — CSRF protection is actually attached, and the login endpoint gets rate-limited.** Closes the "implemented but not enabled" caveat that v0.2.0 carried since day one.
- **P5 — the AMIS mount speaks with one voice.** One pair of ordinary routes instead of twelve overlapping registrations, with the dev-file blocklist enforced on the path that is actually served.
- **P6 — coverage 52% → 65%.**

Public API stays compatible; see *Upgrade notes* for the behavioural changes that are visible to clients.

## Framework (P3)

| | Before (v0.2.x) | After (v0.3.0) |
|---|---|---|
| sanic | 23.6.0（`pip-audit` 报 PYSEC-2026-4162） | **25.12.1**（advisory 清零） |
| sanic-routing / sanic-ext / sanic-testing | 23.6.0 / 23.6.0 / 23.6.0 | 23.12.0 / 25.12.0 / 24.6.0 |
| listener `loop` 参数 | 弃用告警 4 条 | 移除 3 处使用，告警清零 |

**Advisory 清零经双向实证（reviewer `EVT-20261023-010-REVIEW`）**：新栈 `pip-audit --no-deps` 报 **No known vulnerabilities**；正向对照把 sanic 三包回退 23.6.0 重跑同一工具 → PYSEC-2026-4162 阳性复现——既证明修复生效，也证明测量手段本身有效。全量测试独立复测 **299 passed / 0 failed**；compression/database 两蓝图接入 `register_view` 后 10 个错方法用例全部 405 + Allow 正确。

**已知框架行为差异（非缺陷，客户端可见）**：请求体超过 `REQUEST_MAX_SIZE` 时，25 栈的服务端仍正确判定 413（上限生效、body 未被消费、日志记录「框架异常 413」），但**响应写回时客户端通常已因持续发送大 body 而看到连接中断（broken pipe），而不是收到 413 响应**。v0.2.1 发布说明记录的「23.6 下 413 可正常送达」在 25 栈下不再成立。客户端应把「发送大 body 时连接中断」视同超限被拒。

## Security fixes and hardening

### P1 — setting value cap and a request-size limit that works

| Before | After |
|---|---|
| a setting `value` had no length cap; a single write could store up to ~100 MB | the stored value is capped at **8192 characters** (measured on the *stored* representation, so a JSON value is limited by what actually lands in the database); every write path enforces it, and a bulk request is rejected **atomically** when any member exceeds the cap |
| `MAX_CONTENT_LENGTH = 16 MB` was read by nothing (zero references in Sanic 23.6); the real ceiling was `REQUEST_MAX_SIZE` at its 100 MB default, and streamed bodies had none | the dead setting is removed; `REQUEST_MAX_SIZE` is set to **16 MB**, oversize requests are refused |

Measured: values of exactly 8192 are accepted, 8193 rejected on all four write paths (create / update by id / update by key / bulk, atomic); ~16 MiB 边界精确（16,776,267B 通过、16,777,241B 拒绝）。*(reviewer EVT-20261023-006-REVIEW 已核)*

### P2 — CSRF and login rate-limiting

| Before | After |
|---|---|
| `csrf_protect()` existed but was attached to no route — no CSRF protection in force | the session-cookie write path requires the double-submit token; the AMIS console injects it automatically through `requestAdaptor` |
| the login endpoint had no rate limiter — unlimited password guessing | failed logins are limited per **email + IP** (5 failures / 15 minutes, both cache backends), reusing the existing `RateLimitExceededError` |

**Scope note (reviewer-verified, `EVT-20261023-007-REVIEW-02`).** The CSRF check applies to state-changing requests that carry the session cookie and no `Authorization` header. The narrowing is deliberate: a cross-site attacker cannot set custom headers (CORS preflight), so Authorization-carrying clients are immune by construction, and anonymous writes keep their 401 semantics. The reviewer independently confirmed the narrowing holds against SameSite variations, sub-domain cookie injection, path-normalisation tricks and forged forwarding headers.

**Deferred to v0.3.1:** first-login forced password change（强制改密）——评估后推迟；`generate_schemas(safe=True)` 不加列的理由经 reviewer 代码核实成立。

## AMIS console (P5)

| Defect | Before | After |
|---|---|---|
| twelve OpenAPI paths described the same console files (8 sub-directory static mounts + 2 entry-page mounts + 2 ordinary routes, all serving the same tree) | the console is served by **one pair of ordinary routes**: `/amis/` (login page) and `/amis/<path>` (files); the dev-file blocklist is enforced on the *normalized* path, so `./`, `../` and case variants cannot reach `server.js` & friends |
| the file route's parameter was registered with reversed Sanic syntax in v0.2.1 (`<path:__rest__>`) and never matched anything — all files were actually served by the coexisting static mounts | corrected to `<__rest__:path>`; the dead route is now the only mechanism, with 5 content-type regression tests pinning html/json/js/css/png |

Route table: 116 routes / 77 distinct paths → **113 / 67**（发布候选实测；compression/database 接入 register_view 带来 +7 条兜底路由，405 兜底覆盖 path 39 → 46）。OpenAPI 规范 58 条 path（AMIS 相关仅剩 `/amis/` 与 `/amis/{__rest__}` 两条；规范内无任何带 ≥4 方法的 path）。Bare `/amis` stays 404 (docker-acceptance assertion), bare directory paths stay 404, null bytes stay 400.

## Coverage and suite (P6)

`pytest --cov=app`: **52% → 68%**（发布候选实测 5790 语句 / 1880 未覆盖；P6 交付基线为 65%，P1/P2/P3 的新测试在最终候选上再 +3pp），suite **171 → 320 cases**（P6 +94 例 across 7 new files，P1 +17、P2 +22（含限流双维度重写 10 例）、P3 全栈迁移回归；全部带行为断言）。Known uncovered: `app/web/routes.py`（死代码——`frontend/templates/` 不存在）与 `app/cache/redis.py`（需真实 Redis）。compression/database 两蓝图 405 无 Allow 头的缺口已在 **P3 搭车修复**（接入 register_view）。

## Known limitations

- 2FA is still a global switch (`REQUIRE_TWO_FACTOR`); per-account policy remains on the roadmap.
- First-login forced password change is deferred to v0.3.1.
- 在 25 栈下，超过 16MB 的请求体在客户端表现通常为连接中断而非 413 响应（见 Framework 一节）。
- redis cache backend remains untested by the suite (requires a live Redis).
- 非 GET 资源的 405 `Allow` 头在 Sanic 25 下仍会列出 `HEAD`（框架机制层既有行为，与本次改动无关）；已记入后续版本观察项。

## Upgrade notes

- **Behavioural change:** request bodies larger than 16 MB are refused（客户端表现为 413 或连接中断，见 Framework 一节）。大文件上传客户端需遵守上限，或由运维调高 `REQUEST_MAX_SIZE`。
- **Behavioural change:** browser clients that write through the session cookie now need the CSRF token; the bundled AMIS console handles this automatically. API clients using `Authorization` headers are unaffected.
- **Framework upgrade:** Sanic 23.6 → 25.12.1。自带部署（Docker 镜像/pip）无需额外迁移；自建环境按 Sanic 25 官方迁移说明核对自定义中间件。
- `PIP_INDEX_URL` (build-time pip mirror, v0.2.1) keeps its meaning; no configuration migration is expected.
- The [v0.2.1 release notes](v0.2.1-release-notes.md) remain the reference for what v0.2.1 contained.
