# Sanic-Admin v0.3.2 Release Notes

> **Status: released 2026-10-24.** v0.3.2 hardens the authentication flow: it adds first-login forced password change for administrators created from an environment-variable password, fixes two-factor login, and tightens the admin console's role form. **API contract additions:** the login and `/auth/validate-2fa` responses now carry a `must_change_password` boolean, and a new error code `PASSWORD_CHANGE_REQUIRED` (HTTP 403) is returned while a password change is pending. Existing request shapes are unchanged; one manual migration step is required for existing databases.

## Added — first-login forced password change

An administrator created from `INITIAL_ADMIN_PASSWORD` now carries `must_change_password=True`. Until the password is changed, every `/api/**` request from that session answers **403 `PASSWORD_CHANGE_REQUIRED`**; only the login/logout/change-password endpoints, the AMIS console, health and the API docs stay reachable.

- `POST /auth/change-password` accepts `current_password` / `new_password` / `confirm_password`, rejects a new password equal to the current one or shorter than 8 characters, and invalidates all **other** sessions of that account.
- The AMIS login page shows a change-password dialog when the login response carries the flag, so the operator is not locked out of the console.
- Accounts that already changed their password are unaffected; non-administrators and disabled administrators are never flagged.

## Fixed

- **Two-factor login returned 500.** With `REQUIRE_TWO_FACTOR=true` the login response passed a string where a mapping was expected while adding the new flag. The 2FA login branch now returns `{"code": …, "must_change_password": …}`, and `/auth/validate-2fa` also reports the flag.
- **A 2FA-pending session could not complete the second factor while the password change was pending.** `/auth/validate-2fa` is exempt from the forced-password-change block, and `/auth/change-password` now requires that the second factor is already completed (403 otherwise).
- **Response ordering between the forced-password-change check and the `/api` blueprint authentication middleware was not deterministic.** The check is registered as an application-level middleware with an explicit priority so it always runs first; a test pins the order.
- **The AMIS role form rejected `permissions`.** The console submitted the textarea contents as a raw string while the API expects an object, so creating or editing a role answered 400. Both forms now parse the JSON before submitting, validate that the parsed value is an object, mark the field required, and back-fill the stored object as indented JSON when editing.

## Known issue in this release — fixed in v0.3.3

**The admin console's role create/edit dialog did not render at all.** The `permissions` field's
validation was written as a JavaScript **string** in `amis/pages/role-list.json`. AMIS 3.4.0
executes `promisify(schema.validate.bind(...))` while mounting the component, and a string has no
`.bind` — so the form threw `TypeError: i.bind is not a function` and the dialog never appeared.
The API itself was fine; only the browser console was affected.

Fixed in [v0.3.3](v0.3.3-release-notes.md) by restoring `validations.isJson`, which exists in both
the AMIS 3.4.0 and 6.13.0 bundles. This was caught when the repository's E2E gate script was
repaired — that script had been unable to fail, so it had not surfaced the regression.

## Upgrade notes — existing databases

> **Breaking behaviour:** after upgrading and running the migration, any administrator whose password is still `INITIAL_ADMIN_PASSWORD` or the historical default `SAdmin@123` will receive **403 `PASSWORD_CHANGE_REQUIRED`** on every `/api/**` request. They must call `POST /auth/change-password` (or use the console's change-password dialog) before the rest of the API becomes usable again. Plan for this when rolling out to a live installation.

Existing installations (v0.3.1 and earlier) need one manual step, because the project has no migration framework yet and `generate_schemas` does not add columns to existing tables:

```bash
# 1. point the script at the same database the app uses
export SANIC_ENV=production          # or DB_URL=...
export INITIAL_ADMIN_PASSWORD='...'  # the password currently in use
# 2. run it (safe to repeat; it is idempotent)
python scripts/migrate_v0_3_2_must_change_password.py
```

The script adds `account.must_change_password` and then flags every **non-disabled administrator** whose password still equals the current `INITIAL_ADMIN_PASSWORD` **or** the historical hard-coded default `SAdmin@123`. It supports SQLite, MySQL (the production default) and PostgreSQL, and never prints a password. If the administrator's e-mail has been changed since installation (there are administrators but none matching `INITIAL_ADMIN_EMAIL`), it warns and skips creating a new administrator — pass `--create-initial-admin` to create one anyway.

Fresh installations need no migration: `generate_schemas` creates the column.

## Known limitations

Everything listed in the [v0.3.1 release notes](v0.3.1-release-notes.md) still applies, plus:

- **The aerich migration chain is deferred to v0.4 M1.** Its review found the baseline runnable on SQLite but not on MySQL, so v0.3.2 keeps the hand-written migration script above. Automated schema migration arrives with v0.4.
- Login CSRF (the login endpoint is exempt from the double-submit check), `TRUSTED_PROXIES` having no environment-variable wiring, and non-GET 405 `Allow` headers listing `HEAD` on the Sanic 25 stack all remain open, unchanged from v0.3.1.
