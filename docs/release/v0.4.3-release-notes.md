# Sanic-Admin v0.4.3 发布说明

**草稿日期：2026-10-28。**（本文件为发布材料草稿，最终发布日期以 tag 为准。）

---

## 这一版做了什么

**没有新功能，也没有破坏性变更。** 这一版是自 v0.4.2 以来合入 `master` 的提交归集，
内容分三类：

1. **修一个真实缺陷**：生成资源审计日志的 `detail` 字段编码有歧义，字段名含逗号时
   无法无损还原（BL-01，#44）。
2. **补一条缺失的测试防护**：pre-push 测试的进程组 kill 此前只合入了一半，
   超时分支仍会留下孤儿进程（BL-11，#48）。
3. **文档与工程卫生**：纠正若干「说明与实现不符」的陈述（CSRF 保护、`discard_proposal`
   删除条件），补写 `AGENTS.md` 的判据纪律，清理孤儿截图，新增测试入口包装脚本，
   补 `.gitignore` 条目。

一句话：**代码行为只变了一处（审计日志的 `detail` 编码），其余全部是文档、测试与仓库卫生。**

## 修复

### 审计日志 `detail` 的字段名改用 JSON 数组编码（`56c2cbb`，PR #44，BL-01）

**问题**：`detail` 记录「这次改了哪些字段名」，格式 `id=42 fields=<列表>`，此前用
`",".join(fields)` 拼接。规格层允许字段名含逗号，于是两种不同输入编码后完全相同：

```
fields = ["a,b", "c"]   →  "fields=a,b,c"
fields = ["a", "b", "c"] →  "fields=a,b,c"    # 无法区分，无法无损还原
```

**修法**：`app/services/audit.py:152` 由 `",".join(...)` 改为
`json.dumps([...], ensure_ascii=False)`。JSON 数组自定界，任何字段名都能无损往返；
`ensure_ascii=False` 让中文字段名保持可读。`detail` 仍然只记字段名、不记字段值。

**同批核实后判定不需要改动的**：缺陷池 BL-02 称「`fields=sorted(payload)` 无子集校验」。
核实 `render_py.py:286,320` 的 `payload` 已由 `extract_whitelisted(..., WRITE_FIELDS)`
产出，本身即白名单结果，不存在越界字段。

**新增测试**：`tests/test_audit_detail_encoding.py`（123 行，3 个用例）——
`test_detail_field_list_roundtrips_losslessly`（含逗号字段名的往返）、
`test_comma_joined_encoding_would_be_ambiguous`（反向对照：证明旧的逗号拼接确实有歧义）、
`test_detail_omits_fields_when_empty`。

**兼容性**：这是**存储格式变更**，不是读取兼容变更。此前已落库的旧记录仍是逗号拼接格式，
无法与新格式区分。见「升级须知」。

### pre-push 测试补齐进程组 kill（`5e4144b`，PR #48，BL-11）

**问题**：PR #30「修复 pre-push 测试的进程组死锁」实际只合入了一半——
`cat >/dev/null`（读空 stdin）合入了，`Popen(start_new_session=True)` + `os.killpg`
整组杀没合入。核实方式见提交信息：`git show origin/master:tests/test_mcp_write_path.py
| grep -c "_run_git_push_isolated"` → `0`。

**修法**：`tests/test_mcp_write_path.py:84` 新增 `_run_git_push_isolated()`，
子进程以 `start_new_session=True` 启动成为新会话组长，超时分支用
`os.killpg(proc.pid, SIGKILL)` 整组杀掉，避免 `git push` 派生的子进程成为孤儿。

## 已知问题 / 勘误

### 1. v0.4.1 发布说明的树 SHA 错位（已勘误）

v0.4.1 发布说明把「全量测试实际跑的树」写成了发布树。实际 v0.4.1 tag 指向 `133a206`，
而 671 passed 跑在 `c08bd21` 上。两树差异仅 `CHANGELOG.md` 与发布说明本身，
Python 代码为零差异，因此测试数字仍然有效，错的只是「指向哪棵树」这句话。

完整记录见 **[`docs/release/ERRATA.md`](ERRATA.md)** 的「v0.4.1」节。该文件由
`6543d98`（PR #45）新增，v0.4.2 的 `discard_proposal` 描述错误也一并记在其中。

**本版起采用的做法**：把「全量实测树」与「发布树」分开写，并给出读者可自行验证的
`git diff --name-only` 命令。

### 2. AUTH-03 的 confirm 端点尚未接入限流

本版包含 AUTH-03（密码重置两阶段流程）。其 `POST /auth/password-reset/confirm`
端点尚未接入限流，与其他认证端点的处理不一致。

这是功能本身的限制，不随版本演进变化；接入计划见后续版本。

### 3. 已落库的审计日志仍是旧编码

本次修复只改变**新写入**记录的 `detail` 格式。v0.4.3 之前落库的记录仍是
`fields=a,b,c` 逗号格式，无法与新格式区分。需要追溯历史记录的部署请自行处理，
本版不提供回填迁移。

## 升级须知

- **没有数据迁移。** 唯一的代码行为变更在审计日志的 `detail` 编码（见「升级须知」下条）。
- **审计日志 `detail` 格式变了**：`fields=` 后面现在是 JSON 数组（如 `fields=["a","b"]`），
  不再是逗号拼接（`fields=a,b`）。**任何按逗号切分 `detail` 的报表、告警、外部采集脚本
  都要改**，否则会解析出带方括号和引号的字段名。新旧记录混合存在，消费方需兼容两种格式。
- **CSRF 的实际行为没有变，但文档变了**：CSRF 保护自 v0.3.0 起就是全局中间件、默认
  对所有非 GET 请求生效。如果你此前依据旧 README 判断「CSRF 未启用」而绕过了它，
  现在需要重新评估——豁免前缀只有 `/auth/login`、`/auth/register`。
- **`discard_proposal` 的判定比 v0.4.2 说明更严格**：手工创建、没有归属标记的
  `proposal/*` 分支不会被本工具删除。行为一直如此，本版只是把文档改对。
- **测试环境**：建议改用 `scripts/run_tests_safe.sh` 而不是直接 `pytest`，
  它会拒绝把临时产物写进仓库或内盘。未设置 `TMPDIR`/`PYTEST_BASETEMP` 时脚本直接
  `exit 2`（测试不启动），这是预期行为。
