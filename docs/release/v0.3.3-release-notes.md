# Sanic-Admin v0.3.3 Release Notes

> **Status: released 2026-10-24.** v0.3.3 is a hotfix on top of [v0.3.2](v0.3.2-release-notes.md). It fixes a console-side regression introduced in v0.3.2 that made the role create/edit dialog impossible to open, and it repairs the repository's browser E2E gate script — which had never been able to fail, and therefore had never actually protected anything. No API, configuration or deployment change is required.

## Fixed — the admin console's role dialog could not open

| | Before (v0.3.2) | After |
|---|---|---|
| the `permissions` validation in `amis/pages/role-list.json` | written as a JavaScript **string**; AMIS 3.4.0 calls `promisify(schema.validate.bind(...))` while mounting, and a string has no `.bind`, so the component threw `TypeError: i.bind is not a function` | restored `validations.isJson`, which both the AMIS 3.4.0 and 6.13.0 bundles support; the `required` marker and the error message are unchanged |
| consequence | **the role create/edit dialog never rendered** — roles could not be created or edited from the console at all | the dialog opens, and the existing "must parse to a JSON object" behaviour is back |

The API was never affected: `POST/PUT /api/v1/roles` accepted a proper object throughout. Only the
browser console was unusable.

## Fixed — the browser E2E gate script could not fail

`scripts/amis_e2e_check.py` is the repository's console acceptance gate. It had **never passed
legitimately**, and several of its assertions could not fail, so its "green" meant nothing.

| # | Defect | Effect |
|---|---|---|
| 1 | the password field selector was `input[name="password"]` | never matched — the real field is `name="pass"` (`amis/login.html`); login always timed out |
| 2 | the dialog selector was `.amis-dialog` | matched **0** elements on AMIS 3.4.0; the real class is `.amis-dialog-widget` |
| 3 | the cleanup assertion was `... is None or True` | **always true** — the cleanup result was never checked |
| 4 | the role payload used `{"account": ["write"]}` | `write` is not in the permission registry; the backend answered 400 |
| 5 | cleanup took its token from `resp.headers["Authorization"]` | `/auth/login` only sets an HttpOnly `session` cookie plus a `CSRF_TOKEN` header — there is no `Authorization` header, so the token was always `None` and every delete answered 401 |

Two more assertions were silently permissive: an empty AMIS table still renders a placeholder row,
so `tbody tr > 0` was always true; and the total assertion count was not pinned, so a run that
dropped cases still "passed".

**After:** the script uses a real cookie session, sends `X-CSRF-Token` on writes, re-queries after
deleting to confirm the record is gone, and pins the expected assertion count. It also grew
`--new-password` (v0.3.2 makes the first login stop at the change-password form) and a
`--negative-control` mode that deliberately breaks a selector and **requires the assertion to
fail** — proving the gate can actually fail.

Measured: **19/19 assertions pass**, twice in a row, against AMIS 3.4.0 in a real browser. With a
wrong password the script exits non-zero. Both negative controls exit 0 (i.e. the tampered
assertion failed, as it must).

## Added — `amis-e2e` CI job

A new job runs the console gate on every push. **If a browser is not available it is reported as
`skipped`, never as a pass** — a green run now means the browser actually drove the console.

## Upgrade notes

- No configuration change and no data migration. This release touches one page JSON, one script,
  the CI workflow and documentation.
- If you pinned `APP_VERSION` externally, it is now `0.3.3`.

## Known limitations carried over

Everything in the [v0.3.2 release notes](v0.3.2-release-notes.md) still applies. The `permissions`
field continues to be validated as "must parse to a JSON object"; what changed is only *how* the
validation is expressed (AMIS `isJson` rather than a string expression).
