# Sanic-Admin v0.3.3 Release Notes

> **Status: released 2026-10-24.** v0.3.3 is a hotfix on top of [v0.3.2](v0.3.2-release-notes.md). It fixes a console-side regression introduced in v0.3.2 that made the role create/edit dialog impossible to open, and it repairs the repository's browser E2E gate script — which had never been able to fail, and therefore had never actually protected anything. No API, configuration or deployment change is required.

## Fixed — the admin console's role dialog could not open

| | Before (v0.3.2) | After |
|---|---|---|
| the `permissions` validation in `amis/pages/role-list.json` | written as a JavaScript **string**; AMIS 3.4.0 calls `promisify(schema.validate.bind(...))` while mounting, and a string has no `.bind`, so the component threw `TypeError: i.bind is not a function` | restored `validations.isJson`, which both the AMIS 3.4.0 and 6.13.0 bundles support; the `required` marker and the error message are kept |
| consequence | **the role create/edit dialog never rendered** — roles could not be created or edited from the console at all | the dialog opens; the front-end check is JSON-syntax only (see below), the object rule stays with the API |

The API was never affected: `POST/PUT /api/v1/roles` accepted a proper object throughout. Only the
browser console was unusable.

**What `isJson` does and does not check.** `isJson` only asserts that the text parses as JSON —
`null`, an array and a bare number all pass it. The "must be an object" rule is enforced by the
**backend**, in three places: `permissions: [Required(), Type(dict)]` on create
(`app/api/resources/role.py:247`) and `[Type(dict)]` on update (`:307`), plus
`isinstance(permissions, dict)` in `app/auth/permissions.py:295`. So a client submitting `[1,2]`
gets a 400 from the API rather than an inline field error. AMIS 3.4.0 ships no built-in
"is an object" validator, and adding one as a string expression is exactly what broke in v0.3.2 —
the front-end check is therefore intentionally the weaker JSON-syntax check.

## Fixed — the browser E2E gate script could not fail

`scripts/amis_e2e_check.py` is the repository's console acceptance gate. It had **never passed
legitimately**, and several of its assertions could not fail, so its "green" meant nothing.

| # | Defect | Effect |
|---|---|---|
| 1 | the password field selector was `input[name="password"]` | never matched — the real field is `name="pass"` (`amis/login.html`); login always timed out |
| 2 | the dialog selector was `.amis-dialog` | matched **0** elements on AMIS 3.4.0; the real class is `.amis-dialog-widget` |
| 3 | the cleanup assertion was `... is None or True` | **always true** — the cleanup result was never checked |
| 4 | the role payload used `{"account": ["write"]}` | `write` is not in the permission registry; the backend answered 400 |
| 5 | cleanup took its token from `resp.headers["Authorization"]` | `/auth/login` only sets an HttpOnly `session` cookie plus a `csrf_token` cookie — there is no `Authorization` header, so the token was always `None` and every delete answered 401 |

Two more assertions were silently permissive: an empty AMIS table still renders a placeholder row,
so `tbody tr > 0` was always true; and the total assertion count was not pinned, so a run that
dropped cases still "passed".

**After:** the script uses a real cookie session, echoes the `csrf_token` cookie value in the `X-CSRF-Token` header on writes, re-queries after
deleting to confirm the record is gone, and pins the expected assertion count. It also grew
`--new-password` (v0.3.2 makes the first login stop at the change-password form) and a
`--negative-control` mode that deliberately breaks a selector and **requires the assertion to
fail** — proving the gate can actually fail.

Measured: **19/19 assertions pass**, twice in a row, against AMIS 3.4.0 in a real browser. With a
wrong password the script exits non-zero. Both negative controls exit 0 (i.e. the tampered
assertion failed, as it must).

## Added — `amis-e2e` CI job

A new job runs the console gate on every push. **If a browser is not available it is reported as
`skipped`, never as a pass** — a green run now means the browser actually drove the console.

## Upgrade notes

- No configuration change and no data migration. This release touches one page JSON, one script,
  the CI workflow and documentation.
- If you pinned `APP_VERSION` externally, it is now `0.3.3`.

## Correction — the "dashboard cards show no numbers" limitation was wrong

Earlier revisions of these notes carried a known limitation stating that, under AMIS 3.4.0, the
`card` component rendered only `header.title` and `header.subTitle` and left the card `body`
unrendered, so the dashboard tiles showed no figures.

**That claim was mistaken.** It came from inspecting the card HTML through
`inner_html()[:600]`, which cut off right after `.cxd-Card-heading` — the `.cxd-Card-body` that
follows was simply never in the captured string. "I did not see it" was written down as
"AMIS does not render it".

Re-measured in a real browser against AMIS 3.4.0, the body renders normally: each `.cxd-Card`
contains `.cxd-Card-body > .cxd-Card-field > .cxd-Card-fieldValue`, and the first card's text is

```
账户总数
已验证 / 管理员
1
活跃账户：1　管理员：1
```

so the numbers were showing all along. There was never a dashboard defect in v0.3.3, and nothing
was scheduled against it.

The E2E gate nonetheless keeps the stricter assertion the false limitation asked for: it now
compares the rendered figure against `data.accounts.total` from `GET /api/v1/dashboard/summary`
rather than only asserting that a titled card exists. That assertion was validated by a negative
control — changing the page template to `${accounts.totalTYPO}` makes the tile fall back to `0`
while the API returns `1`, and the assertion fails while the other 18 still pass.

## Known limitations carried over

Everything in the [v0.3.2 release notes](v0.3.2-release-notes.md) still applies. The `permissions`
field is still checked on the client for JSON **syntax**; the "must be an object" rule has always
lived in the API (`Type(dict)` in `role.py` plus `isinstance(..., dict)` in `permissions.py`). What
changed in this release is only *how* the client-side check is expressed — AMIS `isJson` instead of
a string expression, the latter being what crashed the dialog.
