# Sanic-Admin v0.3.4 Release Notes

> **Status: released 2026-10-24.** v0.3.4 hardens the authentication path: authentication events
> are now written to the operation log, changing a password requires the current password under a
> rate limit and a stronger new one, and a successful password change rotates the session. **One
> behaviour change is breaking and one makes production refuse to start with a weak initial
> password** — read [Upgrade notes](#upgrade-notes) before deploying.

## Breaking — a password change also ends the current session

`POST /auth/change-password` used to revoke *other* sessions and keep the one that made the
request. It now revokes that one too and issues a fresh session, returned both as a `Set-Cookie`
and in the `Authorization` response header, with `token_rotated: true` in the body.

| Client type | Action needed |
|---|---|
| Browser using cookies (`fetch(credentials: 'same-origin')`) | none — the new `Set-Cookie` is picked up automatically |
| Client that manages its own token | **must** switch to the `Authorization` value in the response, or its next request answers 401 |

Because every session for the account is revoked, two concurrent password changes log each other
out — see [Upgrade notes](#upgrade-notes).

## Breaking — password strength and the rejection list now apply to every write path

Registration, administrator-created accounts and administrator resets were previously not held to
the new rules. They now are: the same strength check and the same rejection list that guard
`POST /auth/change-password` apply wherever a password is set, because the check lives in
`Account.set_password()` rather than in one endpoint. A registration or admin-created account with a
password such as `SAdmin@123` is rejected.

## Breaking — a weak `INITIAL_ADMIN_PASSWORD` stops production

The initial administrator password is now held to the same strength rule as any other password:
at least two character classes, at most 128 characters. Under `SANIC_ENV=production` a value that
fails this raises `ConfigError` **at startup**; under `development` and `testing` it only logs a
warning.

**Check this value before upgrading.** The startup check is a *strength* check only — production
still starts with the stock `SAdmin@123`, because the rejection list deliberately does not apply
here (the initial administrator must be able to use whatever is configured). The rejection list
does apply when a password is *changed*: `SAdmin@123` cannot be reused as a new password. Set this
to a distinct, strong value rather than relying on the stock default.

## Added — authentication events land in the operation log

`OperationLog`, its read-only API and the dashboard's log counters all existed, but **nothing in
the repository ever wrote to it**. `app/services/audit.py` closes that gap for the authentication
path: login success and failure, logout, password change (success, failure, and the 2FA-pending
case) and 2FA success and failure are recorded with `operation_type="auth"`.

Three constraints hold by construction:

- **No credentials are ever written.** Passwords, JWTs and 2FA codes are not passed to the audit
  layer at all; callers describe what happened, not what was supplied.
- **Auditing cannot break the request.** Any failure is swallowed and logged as a warning — the
  audit path is a side channel, not part of the main flow.
- **Client IP follows the existing trust rules.** `X-Forwarded-For` is honoured only when
  `TRUSTED_PROXIES` is configured, reusing the login rate limiter's logic rather than adding a
  second, divergent implementation. Without trusted proxies configured, the recorded address is
  the direct peer and should be treated as approximate.

## Added — rate limiting and strength rules on password changes

Reusing the login rate limiter (counting per account, independently), repeated wrong entries of
the *current* password answer **429** once the window's threshold is reached.

New passwords must have at least two character classes and must not be `SAdmin@123`, the currently
configured `INITIAL_ADMIN_PASSWORD`, or the account's own email. The rejection list and the email
comparison are both **case-insensitive** — `sAdmin@123` is rejected too. Comparison uses
`hmac.compare_digest` over digests, so no plaintext is compared or logged.

The same rules apply everywhere a password is set — **registration, administrator-created accounts,
administrator resets and self-service change** all go through them, not just the change-password
endpoint.

All of this converges on `Account.set_password()`, the single write point for passwords, so every
path — registration, admin-created accounts, admin resets, self-service change — is covered rather
than only the one that happened to be edited. `set_password()` defaults to the **strict** context;
the single caller allowed to skip the rejection list is initial-admin creation, which must be able
to use the configured value.

## Fixed — the v0.3.2 migration script's tests prepared data through the new policy

Three tests in `tests/test_migrate_v0_3_2.py` built v0.3.1-shaped rows with
`Account.set_password()`. The historical default `SAdmin@123` is exactly what that migration script
detects, so the new rejection list blocked the *setup* — the tests measured the password policy
instead of the migration. They now hash directly, bypassing the policy deliberately, with the
reason recorded in the code.

## Upgrade notes

- **Nothing to migrate.** No schema change, no configuration key added or removed.
- **Verify `INITIAL_ADMIN_PASSWORD`** meets the strength rule if you run in production — a weak
  value now stops the process at startup rather than warning.
- **Clients that store the session token themselves** must adopt the rotated token returned by
  `POST /auth/change-password`. Cookie-based browser clients need no change.
- **Concurrent password changes log each other out.** Because a successful change revokes the
  account's other sessions, two sessions changing the same account's password at the same time will
  each invalidate the other; only the last one to finish keeps a live session. This is the intended
  consequence of revoking every session, not a race to work around — do not have two clients change
  the same password at once.
- `APP_VERSION` is now `0.3.4`.
